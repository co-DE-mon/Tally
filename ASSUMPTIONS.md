# Assumptions

Where the spec is silent, these are the choices made.

## Stack

- **Language:** Python
- **Framework:** FastAPI
- **Database:** PostgreSQL

**Reason:** Python with FastAPI was chosen for this assessment, and PostgreSQL for its constraints and transaction support.

**Note:** The assessment spec allows any backend technology and database, so this stack is a free choice.

## Errors and status codes

- **Duplicate `reference_id` on the same account:** 409 Conflict with a plain error message (the original transaction ID is not returned). A retry with the same `reference_id` after a successful first request gets 409 and changes no balance.
- **Insufficient balance:** 422 Unprocessable Entity.
- **Balance would exceed the column limit (`NUMERIC(18,2)`):** a credit that would push the balance past 9999999999999999.99 is refused with 422 and changes nothing.
- **Unknown account:** 404 Not Found.
- **Malformed account ID:** 422 Unprocessable Entity (FastAPI's default for a `UUID` path parameter), like every other validation error.
- **Validation errors:** 422 with code `VALIDATION_ERROR`.
- **Error body:** every error, including unknown routes (404), wrong methods (405) and unexpected failures (500), is `{"error": {"code": "...", "message": "..."}}`. Codes: `ACCOUNT_NOT_FOUND`, `INSUFFICIENT_BALANCE`, `BALANCE_LIMIT_EXCEEDED`, `DUPLICATE_REFERENCE`, `VALIDATION_ERROR`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE`, `SAME_ACCOUNT`. Field detail for validation errors is in the message (for example `amount: Input should be greater than 0`). A 500 never shows the underlying error text. Any other HTTP error from the framework uses the code `HTTP_<status>`.
- **API contract:** `/docs` and `/openapi.json` describe this body for 404, 409, 422 and 500. A 405 carries an `Allow` header; it lists the methods of the first matching route, so it may name only one of the allowed methods.
- **Database connection:** each request opens its own connection with a 5 second connect timeout, so an unreachable database gives a 500 and not a hung request.

## Input rules

- **`description`:** optional; stored as an empty string when omitted; at most 255 characters.
- **`reference_id`:** required; leading and trailing spaces are trimmed (so `"ref-1 "` and `"ref-1"` are the same reference); matching is case-sensitive (`REF-1` and `ref-1` differ); blank after trimming is rejected by the API and by a database CHECK; at most 100 characters. The spec sets no limit; 100 matches the account-name limit and fits UUIDs and prefixed IDs.
- **`type`:** exactly `credit` or `debit`, lowercase. `Credit`, `DEBIT` and `refund` are rejected with 422.
- **`amount`:** greater than 0, at most 2 decimal places, at most 18 digits in total (matches `NUMERIC(18,2)`). A value such as `10.005` is rejected with 422, not rounded.
- **`amount` format:** a plain decimal string of ASCII digits (`"10.50"`), an integer, or a JSON number with at most 15 significant digits (`100.5`). A number with more digits is rejected, because the server's JSON parser turns numbers into floats and could alter them; send those as strings. Booleans, `null`, non-ASCII digits (such as Arabic-Indic or fullwidth), and strings with underscores, spaces, signs or exponents (`"1_0"`, `" 5 "`, `"1e2"`) are rejected with 422.
- **Where the limits are enforced:** the API (422) and the database. The `reference_id` and `description` length limits and `amount > 0` are also database CHECK constraints.
- **Account name:** leading and trailing spaces are trimmed; a name that is blank after trimming is rejected; at most 100 characters. The limit is checked in the API (422) and by a database constraint.
- **NUL characters:** a `name`, `description` or `reference_id` containing a NUL character (`\u0000`) is rejected with 422, because PostgreSQL text cannot store it.
- **Length is checked before trimming:** the limits (100 for `name` and `reference_id`, 255 for `description`) apply to the value as sent. A `reference_id` of 100 characters plus a trailing space is rejected, although it would fit after trimming.

## Money and identifiers

- **Money format:** amounts and balances are strings with two decimals, such as `"10.10"`, so no client float rounds them. The spec does not specify a format.
- **Storage:** `NUMERIC(18,2)` in PostgreSQL. No floating-point type is used anywhere.
- **Identifiers and timestamps:** account `id`, transaction `id` and `created_at` are generated by the system. The client cannot set them, and the initial balance is always 0.

## Responses and concurrency

- **Successful transaction:** 201 with one flat object: the transaction fields and the account's new `balance`.
- **Overdraw check:** the balance is checked and updated in one SQL statement inside the same database transaction as the insert. Concurrent debits on one account are applied one at a time.
- **Rejected requests:** a rejected or duplicate transaction leaves no row and changes no balance.

## History and pagination

- **Endpoint:** `GET /accounts/{id}/transactions?type=&page=&limit=` returns `{data, page, limit, total_records, total_pages}`.
- **Defaults:** `page` 1, `limit` 20. Maximum `limit` is 100.
- **A `limit` above 100:** clamped to 100. The response shows the limit applied and carries an `X-Pagination-Warning` header.
- **Rejected with 422:** `page` below 1, `limit` below 1, non-numeric `page` or `limit`, and a `type` other than `credit` or `debit`.
- **Largest `page`:** 1,000,000. A larger value is rejected with 422; without a cap, a huge `page` made the row offset overflow the database's integer range and returned a 500.
- **A page past the end:** 200 with an empty `data`. `total_pages` is 0 when there are no matching records.
- **Order:** latest first by `created_at`, with `id` descending as a tie-breaker. The `id` is a random UUID, so it keeps page boundaries stable but is not chronological. Concurrent requests on one account queue on its row lock, and `created_at` is taken after the lock is acquired, so history order matches the order in which balances were applied. Two requests on different accounts have no defined relative order.
- **Total and rows:** read in one snapshot (REPEATABLE READ), so `total_records` matches `data` within a request. Fetching a page is fast on any account size (it uses an index), but counting `total_records` reads all of the account's transactions: about 35 ms at 300,000 transactions on one account.
- **Balance:** `GET /accounts/{id}/balance` returns `{account_id, balance}`: the balance as of the read.

## Limits and operating assumptions

- **`reference_id` is a uniqueness key, not an idempotency key.** A repeat of a `reference_id` on the same account returns 409 whatever the other fields say; the original transaction is not returned, and the payload is not compared. A client that lost a response should read the history to find out whether the first request applied.
- **Timeouts:** each wait for a row lock is limited to 5 seconds and each statement to 10 seconds. Past that, or if the database cannot be reached (5 second connect timeout), the response is 503 `SERVICE_UNAVAILABLE` with `Retry-After: 1`, and nothing is stored. A lock held by one stuck transaction fails the waiting requests after about 5 seconds; on a busy account whose queue keeps moving, a request can wait through several lock waits in turn, so the real ceiling is the 10 second statement limit. While one account's lock is held, requests for that account queue and then fail; requests for other accounts are delayed only while the server's worker threads (about 40 per worker) are all in use.
- **Under a slow database link,** requests queued on one account can run into the 10 second statement limit and get 503; a client should retry (nothing was stored). Measured on 2026-10-27 with 80 simultaneous requests on one account: on the same machine as the database all succeeded in under a second; at a 10 ms round trip to the database all succeeded (slowest 6.3 s for transfers); at 50 ms, 61 to 72 of 80 credits and 32 of 80 opposite transfers succeeded and the rest got 503 after about 10 s. In every run the balances matched the stored transactions and no transfer was half done.
- **Concurrency method:** each transaction locks the account row (`SELECT ... FOR UPDATE`), then inserts and updates the balance. A row lock was chosen over `SERIALIZABLE` isolation because only requests on the same account conflict and there are no retries to write.
- **The balance is stored on the account** and changed in the same database transaction as each insert. It is not recomputed from the transactions on every read. A CHECK keeps it at zero or above, and the stress test compares it with the sum of credits minus debits.
- **Money in responses is always a string.** Requests accept the formats listed under Input rules.
- **Extra fields in a request body are ignored,** including a client-supplied `id`, `created_at` or `balance`.
- **No authentication or authorisation.** Anyone who can reach the API can use every account.
- **No request body size limit** is set in the application; a deployment should set one in front of it.
- **Server model:** synchronous routes run in a thread pool (about 40 threads per worker), and each request opens its own database connection. There is no connection pool.
- **Terms:** "transaction" means a ledger entry (a row in `transactions`). "Database transaction" is used for the unit of work that commits or rolls back.

## Immutability

- **Transactions cannot be edited or deleted through the API.** No update or delete route exists. PUT, PATCH and DELETE on the transaction collection or on a transaction ID return 404 or 405 in the standard error body, and change nothing.
- **Resubmitting a `reference_id` with different values** returns 409 and leaves the stored transaction as it was.
- **Not enforced in the database:** a direct SQL UPDATE or DELETE is possible. A trigger was considered and not added.

## Transfers (bonus, spec Section 9)

- **Endpoint:** `POST /transfers` with `source_account_id`, `destination_account_id`, `amount`, `reference_id` and an optional `description`.
- **Recorded as two ordinary ledger entries:** a debit on the source and a credit on the destination, linked by a shared `transfer_id` (a nullable column on `transactions`; `NULL` for ordinary transactions). History, balances and the "balance equals credits minus debits" rule work unchanged, and each leg is immutable.
- **`reference_id` is required** and stored on both legs. It is unique per account as usual, so a transfer is a duplicate (409) if either account already used it. Nothing is stored in that case.
- **Same account as source and destination:** 422 `SAME_ACCOUNT`.
- **Missing account:** 404 `ACCOUNT_NOT_FOUND` (the message does not say which of the two).
- **Atomic:** both inserts and both balance updates are one database transaction. The two account rows are locked in a fixed order (by `id`), so opposite transfers cannot deadlock.
- **Response:** 201 with `transfer_id`, `debit` and `credit`, each in the normal transaction shape with that account's new balance.
