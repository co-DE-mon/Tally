# Transaction Ledger API

HTTP and JSON. Every example below is a real response from the running code.
The same contract is served live at `/docs` (Swagger) and `/openapi.json`.

Choices where the spec is silent are in `ASSUMPTIONS.md`.

## Conventions

- **Content type:** requests with a body must send `Content-Type: application/json`.
- **IDs:** accounts and transactions have UUID ids generated by the server.
- **Timestamps:** `created_at` is set by the server, in ISO 8601 with a UTC offset.
- **Money:** amounts and balances in responses are **strings with two decimals** (`"100.00"`), so no client float can round them. Amounts are exact decimals, never floats.
- **Extra fields** in a request body are ignored. A client cannot set `id`, `created_at` or `balance`.
- **Immutability:** transactions cannot be edited or deleted. There is no update or delete endpoint. `PUT`, `PATCH` and `DELETE` return 404 or 405.
- **Authentication:** none.
- **Browser access (CORS):** only pages served from `http://localhost:5500` or `http://127.0.0.1:5500` (the demo app in `frontend/`) may call the API from a browser, using `GET` and `POST` and the `Content-Type` header. Other origins get no CORS headers, so the browser blocks the response, and a preflight from them (or for another method or header) is answered with 400 `CORS_REJECTED` in the standard error body. This does not restrict `curl` or other non-browser clients, and it is not authentication. The allowed origins are a constant in `app/main.py`.

## Endpoints

| Method and path | Purpose | Success |
|---|---|---|
| `POST /accounts` | Create an account with balance 0 | 201 |
| `POST /accounts/{account_id}/transactions` | Add a credit or debit | 201 |
| `GET /accounts/{account_id}/balance` | Read the current balance | 200 |
| `GET /accounts/{account_id}/transactions` | List transactions, latest first | 200 |
| `POST /transfers` | Move money between two accounts | 201 |

### Create an account

`POST /accounts`

| Field | Type | Rules |
|---|---|---|
| `name` | string | required; leading and trailing spaces are trimmed; not blank; at most 100 characters; no NUL character |

```http
POST /accounts
{"name": "Salary account"}
```

```http
201 Created
{
  "id": "a29db524-6a62-41e3-9a65-7dbdca709d02",
  "name": "Salary account",
  "balance": "0.00",
  "created_at": "2026-10-27T03:36:53.619561+05:30"
}
```

The balance always starts at 0. A `balance` sent by the client is ignored.

### Add a transaction

`POST /accounts/{account_id}/transactions`

| Field | Type | Rules |
|---|---|---|
| `type` | string | required; exactly `credit` or `debit`, lowercase |
| `amount` | decimal | required; greater than 0; at most 2 decimal places; at most 18 digits in total. Send a string (`"100.00"`), an integer, or a JSON number with at most 15 significant digits. Rejected: `NaN`, `Infinity`, exponents (`"1e2"`), underscores, spaces, signs, non-ASCII digits, booleans, `null` |
| `reference_id` | string | required; trimmed; not blank; at most 100 characters; case-sensitive; unique **per account** |
| `description` | string | optional (stored as `""` if omitted); at most 255 characters |

A credit increases the balance and a debit decreases it. A debit that would make the balance negative is refused. The insert and the balance update happen in one database transaction: a refused, duplicate or failed request stores no row and changes no balance.

```http
POST /accounts/a29db524-6a62-41e3-9a65-7dbdca709d02/transactions
{"type": "credit", "amount": "100.00", "description": "salary", "reference_id": "ref-1"}
```

```http
201 Created
{
  "id": "8bbb341b-dc1c-47a7-bf10-10a90fe3908a",
  "account_id": "a29db524-6a62-41e3-9a65-7dbdca709d02",
  "type": "credit",
  "amount": "100.00",
  "description": "salary",
  "reference_id": "ref-1",
  "transfer_id": null,
  "created_at": "2026-10-27T03:36:53.654439+05:30",
  "balance": "100.00"
}
```

`balance` is the account's new balance after this transaction. `transfer_id` is `null` for an ordinary transaction.

A repeated `reference_id` on the same account returns 409 and changes nothing, whatever the other fields say. The original transaction is not returned. `reference_id` is a uniqueness key, not an idempotency key. The same `reference_id` may be used on different accounts.

### Transfer between accounts

`POST /transfers`

| Field | Type | Rules |
|---|---|---|
| `source_account_id` | UUID | required; the account that is debited |
| `destination_account_id` | UUID | required; the account that is credited; must differ from the source |
| `amount` | decimal | required; same rules as a transaction amount |
| `reference_id` | string | required; same rules as a transaction `reference_id`; stored on **both** legs |
| `description` | string | optional; at most 255 characters; stored on both legs |

A transfer is recorded as two ordinary ledger entries: a **debit** on the source and a **credit** on the destination. Both carry the same `transfer_id`. Both accounts' balances change in the same database transaction: if anything fails (insufficient funds, a missing account, a duplicate `reference_id` on either account, a failure while crediting), neither leg is stored and neither balance changes.

```http
POST /transfers
{
  "source_account_id": "27d229fb-4f79-44e8-8186-1238fb4b2b30",
  "destination_account_id": "fa888544-2b9a-4144-9cfc-b96cec7ed80d",
  "amount": "30.00",
  "description": "rent share",
  "reference_id": "tr-1"
}
```

```http
201 Created
{
  "transfer_id": "91225b22-e106-494d-9403-7180b35cddda",
  "debit": {
    "id": "57ce880b-c0fd-41b1-a222-a1d7bd288600",
    "account_id": "27d229fb-4f79-44e8-8186-1238fb4b2b30",
    "type": "debit",
    "amount": "30.00",
    "description": "rent share",
    "reference_id": "tr-1",
    "transfer_id": "91225b22-e106-494d-9403-7180b35cddda",
    "created_at": "2026-10-27T03:58:41.403412+05:30",
    "balance": "70.00"
  },
  "credit": {
    "id": "43066a4d-9bf0-44c2-954f-4354a88a549d",
    "account_id": "fa888544-2b9a-4144-9cfc-b96cec7ed80d",
    "type": "credit",
    "amount": "30.00",
    "description": "rent share",
    "reference_id": "tr-1",
    "transfer_id": "91225b22-e106-494d-9403-7180b35cddda",
    "created_at": "2026-10-27T03:58:41.404882+05:30",
    "balance": "80.00"
  }
}
```

Each leg's `balance` is that account's new balance. Each leg then appears in its own account's history, with the same `transfer_id`. Transfers are immutable like any other transaction.

The `reference_id` is unique per account, so a transfer is a duplicate (409) if **either** account already used it. The source and destination rows are locked in a fixed order, so two opposite transfers at the same time cannot deadlock.

### Get the balance

`GET /accounts/{account_id}/balance`

```http
200 OK
{"account_id": "a29db524-6a62-41e3-9a65-7dbdca709d02", "balance": "70.00"}
```

The balance is the value at the moment of the read.

### Get the transaction history

`GET /accounts/{account_id}/transactions`

| Query parameter | Default | Rules |
|---|---|---|
| `type` | none (both types) | `credit` or `debit` |
| `page` | 1 | 1 to 1,000,000 |
| `limit` | 20 | at least 1; a value above 100 is **clamped to 100** (see below) |

Transactions are ordered latest first by `created_at`, with `id` descending as a tie-breaker. `total_records` and `total_pages` count the transactions that match the `type` filter. `total_pages` is 0 when nothing matches. A page past the end returns 200 with an empty `data`.

```http
GET /accounts/a29db524-6a62-41e3-9a65-7dbdca709d02/transactions?limit=1&page=1
```

```http
200 OK
{
  "data": [
    {
      "id": "be16d4f7-11bb-4997-8b82-35876a2c6b55",
      "account_id": "a29db524-6a62-41e3-9a65-7dbdca709d02",
      "type": "debit",
      "amount": "30.00",
      "description": "rent",
      "reference_id": "ref-2",
      "transfer_id": null,
      "created_at": "2026-10-27T03:36:53.676512+05:30"
    }
  ],
  "page": 1,
  "limit": 1,
  "total_records": 2,
  "total_pages": 2
}
```

The count and the rows are read in one snapshot, so `total_records` matches `data` within one request. Between two page requests a new transaction can shift the rows (offset paging), so a row may appear on two pages.

**Clamped limit:** `?limit=500` returns 200 with at most 100 rows, `"limit": 100` in the body, and the header `X-Pagination-Warning: limit clamped to 100`. Other invalid values (`page=0`, `limit=0`, `limit=abc`, `type=refund`) return 422.

## Errors

Every error, including an unknown route or an unexpected failure, has one body:

```json
{"error": {"code": "ACCOUNT_NOT_FOUND", "message": "Account not found"}}
```

`code` is stable and meant for programs. `message` is for people and may change.

| Status | Code | When |
|---|---|---|
| 404 | `ACCOUNT_NOT_FOUND` | no account has this id (for a transfer: the source or the destination) |
| 400 | `CORS_REJECTED` | a browser preflight (`OPTIONS` with an `Origin` header) from an origin, or for a method or header, that is not allowed; see Conventions |
| 404 | `NOT_FOUND` | unknown route |
| 405 | `METHOD_NOT_ALLOWED` | wrong method for a route; carries an `Allow` header |
| 409 | `DUPLICATE_REFERENCE` | the `reference_id` is already used on this account (for a transfer: on either account) |
| 422 | `VALIDATION_ERROR` | invalid input: body, query parameter or path (including a malformed account id). The `message` names the field, for example `amount: Input should be greater than 0` |
| 422 | `INSUFFICIENT_BALANCE` | a debit, or the source of a transfer, would go below zero |
| 422 | `SAME_ACCOUNT` | a transfer names the same account as source and destination |
| 422 | `BALANCE_LIMIT_EXCEEDED` | a credit (or the destination of a transfer) would push the balance past 9999999999999999.99 |
| 500 | `INTERNAL_ERROR` | unexpected failure; the message is generic and never shows internal details |
| 503 | `SERVICE_UNAVAILABLE` | the database is busy or unreachable; carries `Retry-After: 1`; nothing was stored |
| other | `HTTP_<status>` | any other HTTP error raised by the framework |

Examples:

```http
409 Conflict
{"error": {"code": "DUPLICATE_REFERENCE", "message": "This reference_id is already used on this account"}}
```

```http
422 Unprocessable Entity
{"error": {"code": "INSUFFICIENT_BALANCE", "message": "Insufficient balance"}}
```

```http
422 Unprocessable Entity
{"error": {"code": "VALIDATION_ERROR", "message": "amount: Input should be greater than 0"}}
```

```http
405 Method Not Allowed
{"error": {"code": "METHOD_NOT_ALLOWED", "message": "Method Not Allowed"}}
```

On a 405 the `Allow` header lists the methods of the first matching route, so it may name only one of the allowed methods.

## Behaviour under load

- Requests on one account are applied one at a time (each transaction locks the account row; a transfer locks both, in a fixed order), and `created_at` is taken after the lock, so history order matches the order balances were applied.
- **Timeouts:** each wait for a row lock is limited to 5 seconds and each statement to 10 seconds; the connection to the database times out after 5 seconds. A request that hits a limit returns 503 and stores nothing. If the lock is held by one stuck transaction, waiting requests fail after about 5 seconds. If the account is busy and its queue keeps moving, a request can wait through several lock waits in turn, so it can take up to about 10 seconds (the statement limit) before it succeeds or returns 503.
- The server runs synchronous routes in a thread pool of about 40 threads per worker, with one database connection per request and no connection pool.
- If the database is unreachable or all of its connections are in use, the response is 503 `SERVICE_UNAVAILABLE` and nothing is stored, so the request can be retried. With a slow network between the server and the database, a burst of requests on one account can also exceed the 5 second lock wait; those requests get 503 too.
- No request body size limit is set by the application.
